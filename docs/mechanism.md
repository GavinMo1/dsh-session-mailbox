# 它是怎么工作的

README 只讲用起来是什么样。这一份讲投递、来源、界面、压缩通知和记账那些「为什么看起来是这样」的细节。取舍论证在 [DESIGN.md](../DESIGN.md)，不变量在 [AGENTS.md](../AGENTS.md)。

## 一条消息的两步

`send_session_message` 做两件事，都不可省：

1. **归因后塞进对方的收件箱**：`agents.withoutInitiator(...)` 包住收件箱的 splice，跟 Web UI 发一条 prompt 是同一个归因。这样对方不会被记成「发送方那一轮发起的工作」，它自己是一个 runtime root。
2. **立刻落盘一次**：`sessions.flush`，把「已进内存收件箱」到「写进持久转录」之间那个窗口缩短，免得对方下一次写盘前重启就丢。

两件事的失败处理不一样，这一点是故意的：**flush 失败不改写「已投递」**——把已接收报成没送到是另一种谎。所以：

> `queued: true` 只表示「它进了对方的收件箱」，不表示对方读到了。要确认到达，让它回信。

## 消息的来源是结构，不是文本

落进对方转录的那条消息，`source` 用的是宿主给「一个 agent 发给另一个 agent」定的三键：

```json
{ "kind": "agent-message", "form": "relay", "senderSessionId": "session-…" }
```

三键是宿主的，不是我们的：多一个键或少一个键，宿主的会话格式校验会抛 `SessionFormatError`；`form` 用 `relay`（另一个 agent 说给它的话），不用 `notice`（那表示运行时在陈述某个子代理的下场）。

因此这条消息**在宿主眼里不是 user 消息**：

- 网页里它不是用户气泡，而是一行折叠的「上下文注入」（宿主对所有非 `user` 来源的统一处理）；
- 展开后第一行是 `from session <会话 id>`，然后是正文——发送方是谁，界面直接写出来；
- 如果这条消息**唤醒**了一个空闲会话，它会成为新一轮的第一步，那一行会比较醒目。

模型读到的只有正文文本（`Agent <短名> sent a message:` + 可选的 `来自「标题」` 一行 + 你的话），**读不到来源字段**。所以回信地址靠短名：短名就是 `send_session_message` 认的地址之一。

要程序化区分「agent 发来的」和「人打的」，读 `source.kind`，不要读正文——正文谁都能写，来源是运行时给的。

## 插话还是开新回合

由目标当时的状态决定，不是参数（`lib/pure.js` 的 `primitiveFor`）：

| 对方状态 | 我们用的原语 | 落在哪 |
|---|---|---|
| `running` | `steer` | 对方**当前回合**的下一步 |
| 其它 | `followup` | 给它开新一轮，消息是第一步 |

宿主的循环在**步骤之间**只领取 next-step 输入，在**轮次边界**才连排队提示词一起领取。所以插话的落点是「下一个步骤边界」：它不会抢占正在执行的那个工具调用——对方正在跑一条 90 秒的前台命令，消息要等那个调用返回，但仍落在同一个回合里。

返回值里的 `primitive` 就是这次走了哪条，调用方不必猜。

**已知缺口**：没有参数可以强制「排队等对方这一轮结束」。对正在跑的会话，插话是唯一选项。见[已知边界](boundaries.md)。

## 冷会话

不在本进程里的会话，`send_session_message` / `rename_session` / `compact_session` 会用宿主的 `sessionController.resolveAgent` 把它从磁盘装载起来（读转录 → 解析并 mount agent preset → 发布 Agent）。

- 只能按**完整 id** 点名：冷态下它的标题和短名解析不出来，因为那张表来自活会话；
- 装载之后它就留在内存里，插件不提供卸载，直到 DSH 重启；
- 失败会给具名原因：`sessionController` 不可用 / 找不到 / 被别的 writer 占着 / 属于子代理路由。

## 压缩通知的四条出路

`compact_session` 只负责「开压」，结果靠一条消息回来（走 `followup`，故意不用 `steer`：状态消息没资格打断别人手上那一步）。通知有四种措辞，取决于能读到什么：

| 情况 | 通知里写的 |
|---|---|
| 前后都读到 | `压缩完成：<会话> 12,345 → 8,901 tokens（少了 3,444）` |
| 只读到压缩前 | `压缩完成：<会话> 12,345 → ? tokens（没有压缩后的大小）` |
| 只读到压缩后 | `压缩完成：<会话> ? → 8,901 tokens（没有压缩前的大小）` |
| 一个都读不到（这台 DSH 没挂 token 计量器） | `压缩完成：<会话> 压了，但读不到前后大小` |

**缺的一端写 `?`，两端都缺就说读不到，绝不编 0**——0 会读成「这个会话是空的」。数字来自 `tokenMeter.measure()`（按日志重放，压缩一落盘就变），不是 `contextPressure()`（那只是上一次模型调用的 prompt 大小，要等下一次调用才动）。

失败的通知长这样：`这次没压成：<会话>：<原因>。没排队也没重试，可以再发一次。` 原因一般是宿主自己的文案（比如它在压缩中途报的忙），我们不重写。

两个坑：

- **DSH 在压缩途中重启，那一次不会有完成通知。** 完成通知只是内存里一个 detached 任务的结果。按「没压」处理，重发一次即可。
- **「同一目标正在压」只在进程内存里。** 压缩进行中 `agent.status` 仍报 `idle`，所以判据只能是插件自己的集合：第二次调用回 `already-running`。跨进程（桌面端 / web）各有一份，那种重复压缩由宿主的 `/compact` 自己报忙。

## 「已回信 / 未回信」怎么来的

**一个写入点，两个方向地读。** 每条消息都是经 `send_session_message` 出去的，所以发送方记一条边 `from → to` 就够了：

| 想知道 | 读哪条边 |
|---|---|
| 我最后发给 X 的时间 | `我 → X` |
| X 最后发给我的时间 | `X → 我` |
| 「它回过信了」 | 存在 `X → 我` 这条边 |

`list_sessions` 的行尾就是这张表的方向读数，**不解析任何消息前缀**——结构信息降级成字符串再猜回来，格式一变就静默失效。

落盘文件（`lib/peerstore.js`）：

| 平台 | 路径 |
|---|---|
| Windows | `%LOCALAPPDATA%\dsh-session-mailbox\peers.json` |
| macOS | `~/Library/Application Support/dsh-session-mailbox/peers.json` |
| Linux | `$XDG_STATE_HOME/dsh-session-mailbox/peers.json`（没设则是 `~/.local/state/dsh-session-mailbox/peers.json`） |

测试或临时环境可以用环境变量 `SESSION_MAILBOX_STATE` 指到别处。

读这个文件的三条规矩：

- **读从不写**：不建目录、不清理、不修坏文件。读坏主文件时退回同目录的 `.bak`，仅此一次。
- **读不到 = 无记录**，不是「没回信」。文件缺失、坏掉、版本不认识时列表照常出，只是行尾没有后缀。所以「没后缀」和「没回过信」是两件事。
- **上限 200 条，只在写时淘汰**（最久未用的先丢）。读时淘汰会让「读」变成一次修改，正好删掉别人正在找的证据。

时间取的是**消息被铸出来的那一刻**（发送方调用工具的时间），不是文件的 mtime——复制、备份、同步都会改 mtime。

## 收信方还没有工具的那个窗口

插件是 bundle 级的：装好、重启之后，**所有** top-level 会话都有这八个工具。真正的窗口只在「已经装好但还没重启」和「插件被关掉」这两种情况：消息能进来，回信工具不在。

一句话判据：**你的工具表里有没有 `send_session_message`？** 没有就是插件没挂上——在这种情况下回信只能由人在 GUI 里打字，或者把插件打开/重启后用工具回。

顺便说清一件事：本插件的投递走进程内服务，从来没有经过 HTTP。DSH 的 `/api` 自 0.2.2-rc.1 起只认 v2 operator 凭据（那东西只能用每进程的 launchToken 换），任何「插件去调 Web 路由」的写法在这个版本上都已经不通，别再改回去。
